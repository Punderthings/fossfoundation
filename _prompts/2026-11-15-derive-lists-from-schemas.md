# Derive field lists and similar lists from schemas

2026-11-15 · Shane Curcuru, with Claude

Status: decided (2026-11-15); implementation in progress. **SC:** comments added to draft.

## Prompt

> Review the code, schemas, and any documentation that includes tables or lists that may
> be lists of fieldnames or the like. In the context of PR #102, are there any other
> places in the repository that we can simplify maintenance of code or docs that have
> fields, lists, or the like, by instead including more data in a schema or other simple
> hand-edited file, and then using a small parser like catalog.py or a Jekyll or build
> time tool to instead derive that data from the current schemas.

## The pattern from PR #102

PR #102 moved fdncheck's per-field check class out of a Python table and into the
foundations schema as an `x-check` keyword on each property.
[`catalog.py`](../assets/python/fdncheck/src/fdncheck/records/catalog.py) now reads the
schema, keeps only the policy for each class in code, and a test fails if any field is
missing a valid `x-check`. One hand-edited source, a small reader, and a test that keeps
them in step.

This review applies the same idea elsewhere. For each place, it names the single source,
what would derive from it, and the rough effort and benefit. Nothing here is implemented
yet.

## Two ways to derive

- **At site build time, in Liquid.** Jekyll already loads every file in `_data/` as
  `site.data`, including the schemas: `site.data["foundations-schema"].properties` is the
  foundations schema's properties, in file order. A template can loop over it, so the
  page is always current and nothing has to be regenerated. This needs no new tool or
  dependency, and suits site pages and layouts.
- **In a tool, with a test.** Where code needs the list (Ruby or Python), the tool reads
  the schema at run time, as `catalog.py` does. Where reading it isn't worth it, a test
  checks that the code's copy equals the schema's. Files that are not built by Jekyll,
  such as `AGENTS.md`, `REUSE.toml` and the OpenAPI files, either get generated by a tool
  or get a test that checks them.

## Findings, most useful first

### 1. Foundation page fields: `_includes/foundation-fields.html`

**Today.** All 60 foundation fields are written out by hand, each with its schema
`title` and `description` copied into an `<abbr>`. This file was once generated by
`schema_utils.rb -a liquid` (`schema2liquid`), then hand-edited for special cases: the
Wikidata link, the `jjresolver` lookups for `conductSource` and `subOrganization`, the
US-dollar check, and the taxes and sponsorships includes. Regenerating it now would lose
those edits, so nobody does.

**Drift found.** `fiscalHost`, added to the schema in PR #102, is not shown on foundation
pages. `foundation-single.html` (the listing entry) uses a different description for
`nonprofitStatus` than the schema does.

**Proposal.** Replace the hand-written field lines with one Liquid loop over
`site.data["foundations-schema"].properties`, starting a new `<section>` at each
`section` keyword. Render each value from what the schema already says:

| Schema says | Rendered as |
| --- | --- |
| `format: url` | a link |
| `format: urlfragment~<prefix>` | a link to `<prefix><value>` (Wikidata today) |
| `format: jjresolver~<collection>~...~<prefix>` | a name looked up in that collection, linked |
| `type: array` | a list of the above |
| anything else | the plain value |

The few fields shown by other includes (`sponsorurl`, `sponsorList`, `sponsorships`, shown
by `foundation-sponsorships.html`) would be marked with one new keyword, for example
`"x-display": "foundation-sponsorships.html"`, so the loop calls that include instead of
printing the field. The taxes include and the US-dollar logic stay as they are, after the
loop's Funding fields. **SC:** Agreed, except call the new keyword "x-includes" to match the `_includes` directory where those Jekyll files are kept.

**Effort and benefit.** Small to medium. Benefit is high: a new or renamed field, title or
description shows up on all 95 foundation pages with no template edit. It can be checked
by building the site before and after and diffing `_site/foundations/`; the only
expected change is that `fiscalHost` appears. `schema2liquid` can then be removed.

### 2. Foundation field order and template: `schema_utils.rb` and `foundation-template.md`

**Today.** `FOUNDATION_FIELDNAMES` in
[`schema_utils.rb`](../assets/ruby/schema_utils.rb) is a hand-copied list of field names
that `-a normalize` uses to order front matter. Its own comment says
`TODO: coordinate with schema definition automatically`.
`_data/foundation-template.md` is the other copy, generated once by `-a liquid`.

**Drift found.** `FOUNDATION_FIELDNAMES` is missing `fiscalHost`, `conductProjects` and
`conductReport` (and, on purpose, `dissolutionDate`), so normalize moves those three to the
end of every record. The template is missing `fiscalHost`.

**Proposal.** Read the field order from the schema's `properties`, skipping fields whose
`$comment` starts with `EXCLUDE`, as `schema2template` already does. Add a minitest that
the template's keys equal that list, so a schema change without a template change fails.

**Effort and benefit.** Small. Prevents a quiet reordering of records the next time
anyone runs normalize.

### 3. OpenAPI v1 foundation schema: `openapi/v1/foundation-schema.yaml`

**Today.** [`fdnmodel.md`](../_pages/fdnmodel.md) says the OpenAPI schema "is derived from"
`foundations-schema.json`, and [`openapi.md`](../_pages/openapi.md) says front matter
fields "match" it, but it is a separate hand-edited copy.

**Drift found.** Eight schema fields are missing from the OpenAPI file (`contacturl`,
`teamurl`, `missionurl`, `eventurl`, `donateurl`, `securityurl`, `conductProjects`,
`conductReport`), it has one field the schema doesn't (`uniqueEntityID`), 28 of the shared
fields have a different title or description, and `conductSource` is a string there but
an array in the schema.

**Proposal.** Generate the `Foundation` component from the JSON Schema with a small
addition to [`openapi_builder.rb`](../assets/ruby/openapi_builder.rb) (stdlib `json` and
`yaml` only), dropping our `x-` and `section` keywords or keeping them as OpenAPI
extensions. The v2 OpenAPI description planned in the
[URL standards plan](2026-11-01-url-standards-for-datasets.md) could instead `$ref` the
published JSON Schemas directly, since OpenAPI 3.1 uses JSON Schema.

**Effort and benefit.** Small to medium. This changes a published API description, so it
needs a maintainer's decision first (open question 2).

### 4. Sponsorship metalevels

**Today.** The ordered list of metalevels (`first` ... `eighth`, `community`, the in-kind
levels, `startuppartners`, `academic`, `enduser`, `grants`, `listed`) is kept in four
places: `SPONSOR_METALEVELS` in
[`sponsor_utils.rb`](../assets/ruby/sponsor_utils.rb), the display labels in
`_data/sponsorship-levels.json`, the `levels` properties in `sponsorships-schema.json`,
and the prose on [`sponsorships.md`](../_pages/sponsorships.md). Which levels are in-kind
is decided by a regular expression (`/inkind/`) in `sponsor_reports.rb`.

**Drift found.** The schema's `levels` is missing `startuppartners`, `academic`, `enduser`
and `listed`, which the code and labels both have.

**Proposal.** Make the schema's `levels.properties` the single source, in order, each with
`title` (the display label now in `sponsorship-levels.json`), `description`, and an
`x-inkind: true` keyword where it applies. Ruby reads the order and the in-kind set from
the schema; `sponsorship.html` reads the label from
`site.data["sponsorships-schema"].properties.levels.properties[name].title`. Then
`sponsorship-levels.json` can be removed (open question 3), or kept and generated.

Also in this file: `SOURCE_TYPES` in `sponsor_utils.rb` is a copy of the schema's
`sourcetype` enum. A one-line test that they are equal is enough.

**Effort and benefit.** Small to medium. Benefit is medium: new levels are rare, but when
one is added today it has to be added in four places, and one copy is already behind.

### 5. Sponsorship page and docs fields

**Today.** `_layouts/sponsorship.html` writes out each model field, level field and
benefit with a hand-copied title and description, and the "Model Structure" list on
`sponsorships.md` describes the same fields again in prose. Both largely repeat
`sponsorships-schema.json` and `sponsorshiplevels-schema.json`.

**Proposal.** Reuse the include from finding 1 for the model fields and level fields. For
the docs page, render the field list from the schemas with a small loop, keeping the
introductory prose by hand.

**Effort and benefit.** Medium, because the layout mixes fields with the history and income
tables. Do it after finding 1, so the include already exists.

### 6. Crosswalk fields, terms and evidence types

**Today.** This is the dataset with the highest bar, and its definitions are kept in three
places that have to agree:

- the field-to-standard-term mapping: `$comment` links in `crosswalk-schema.json`,
  `context()` and `vocabulary()` in
  [`export.py`](../assets/python/fdncrosswalk/src/fdncrosswalk/export.py), and the
  "Field / Standard term / Meaning" tables in [`crosswalk.md`](../_pages/crosswalk.md);
- the evidence types: the schema's `type` enum, the strength and freshness sets in
  [`crosswalk.py`](../assets/python/fdncrosswalk/src/fdncrosswalk/crosswalk.py)
  (`CONFIRMING`, `SUPPORTING`, `LONG_LIVED`), and the "Type / Who asserts it / Gives"
  table on `crosswalk.md`;
- the attestation methods, listed in both `crosswalk-schema.json` and
  `attestations-schema.json` (which adds `self`), and again in `crosswalk.md`.

No drift found today, which is to the credit of the people who kept them in step by
hand.

**Proposal.** Put the terms in the schema and derive the rest:

- On each property, an `x-term` keyword with the CURIE (`schema:identifier`,
  `dcterms:source`, `fdn:platform`). `context()` builds from those; `vocabulary()` takes
  each `fdn:` term's label and comment from the property's `title` and `description`.
  This also follows the AGENTS.md rule that each field documents the term it maps to.
- For evidence types, replace the plain `enum` with the standard JSON Schema form for a
  documented enum, `oneOf` of `{"const": ..., "description": ...}`, plus `x-gives`
  (confirmed, probable, unconfirmed, rejected) and `x-freshness-days`. `crosswalk.py`
  builds its sets from those, and a test keeps them valid.
- `crosswalk.md` renders both tables from `site.data["crosswalk-schema"]`, keeping the
  explanatory prose by hand.
- Attestation methods: define them once (for example in `attestations-schema.json`) and
  `$ref` them from the crosswalk schema.

**Effort and benefit.** Medium. Benefit is high because a mismatch here would change a
computed confidence, which readers take as a statement about a foundation's control of a
namespace. Changing `confidence` rules stays a reviewed change to `crosswalk.py`; only
the lists move.

A smaller, related item: the platform tables in
[`ecosystems.py`](../assets/python/fdncrosswalk/src/fdncrosswalk/ecosystems.py)
(`REPO_HOSTS`, `NAMESPACE_REGISTRIES`, `PURL_REGISTRIES`) restate the schema's `platform`
enum. A test that every enum value is in exactly one of them, or explicitly in none, is
enough.

### 7. One list of datasets

**Today.** The list of datasets, where each lives, its schema, license and how it is
maintained is written by hand in at least five places: the datasets table and the sourcing
table on [`data.md`](../_pages/data.md), the repository map in `AGENTS.md`, the files table
on `crosswalk-files.md`, the v2 dataset lists on `openapi.md`, and the CC0 overrides in
`REUSE.toml`. The [URL standards plan](2026-11-01-url-standards-for-datasets.md) adds a
sixth, the DCAT catalog at `/api/v2/catalog.jsonld` (its step 4).

**Proposal.** Add one hand-edited registry, `_data/datasets.yml` (CC0-1.0), with one entry
per dataset: identifier, title, page, paths, schemas, license, how it is maintained and by
which tool, update frequency, and the sourcing columns from the data sourcing table.
Derive from it:

- both tables on `data.md`, in Liquid;
- `/api/v2/catalog.jsonld` as a Jekyll page using `jsonify`, and the Schema.org
  `Dataset` blocks on each dataset page, both already planned;
- tests that every dataset's paths exist, and that every CC0 dataset has a matching
  `REUSE.toml` override.

`AGENTS.md` stays hand-written, because agents read it raw from the repository and it
explains more than a table can. It can link to the registry for the full list.

**Effort and benefit.** Medium. It is the base the DCAT catalog needs anyway, so it is
cheapest to do as part of that step. A new data file needs a maintainer's approval (open
question 4).

### 8. Smaller items

- **`_data/fiscalhost-map.json`** maps `lf` and `spi` to names that are already each
  foundation's `commonName`. `sponsorship.html` can look the name up in `site.foundations`
  instead, and the file can be removed.
- **Collection lists in code.** `LOCAL_COLLECTIONS` in `catalog.py` and `OTHER_ID_DIRS` in
  `sponsors.rb` restate the collections in `_config.yml`. Both can read `_config.yml`, or a
  test can compare them.
- **`nonprofitStatus` values.** The US nonprofit types are hard-coded in two templates: the
  US-dollar check in `foundation-fields.html` and the 501(c)(3) and 501(c)(6) columns in
  `_layouts/categories.html`. The schema has a `TODO: enum based on
  https://schema.org/NonprofitType`. Today's records hold 19 different values, several in
  free text, so an enum first needs a data cleanup. Defer it (open question 5).
- **Hosted projects.** The `projects-*.csv` files have no schema, and each foundation has
  its own nearly identical page. A [CSVW](https://www.w3.org/TR/tabular-metadata/) or
  [Table Schema](https://datapackage.org/standard/table-schema/) description, which the
  URL standards plan already expects for CSV datasets, would document the columns once,
  and the pages could be generated from the registry in finding 7. Low priority. **SC:** For now, ignore these example `projects-*.csv` files; they were an experiment; add a future task to re-design how we store and display these; leave them alone until them.
- **Ruby test commands in `AGENTS.md`.** Each test file is listed by name, so a new test
  file is easy to miss. A loop over `assets/ruby/test/*_test.rb` would always run them
  all. Changing `AGENTS.md` needs a maintainer's go-ahead.

## Suggested order

Each step is one pull request that can be reviewed on its own.

1. Findings 1 and 2: foundation fields, order and template from the schema. A site diff
   shows the change is safe.
2. Finding 4: sponsorship metalevels and `SOURCE_TYPES`.
3. Finding 3: OpenAPI v1, after open question 2 is decided.
4. Finding 6: crosswalk terms and evidence types.
5. Finding 7: the dataset registry, together with the DCAT catalog step of the URL
   standards plan.
6. Finding 5 and the smaller items as time allows.

## Open questions

1. **New schema keywords.** Findings 1, 4 and 6 add `x-` keywords to schemas
   (`x-display`, `x-inkind`, `x-term`, `x-gives`, `x-freshness-days`), following
   `x-check` from PR #102. Is that the convention to use, and should each schema's
   top-level `$comment` document its `x-` keywords, as the foundations schema now does
   for `x-check`? **SC:** Agreed.
2. **OpenAPI v1.** Generate `openapi/v1/foundation-schema.yaml` from the JSON Schema, which
   adds eight fields, removes `uniqueEntityID`, and changes `conductSource` to an array in
   the published description? Or freeze v1 as it is and only derive v2? **SC:** Generate a new v1 schema; these are only additions, and they will be valuable to previous users still using that version; call it version 1.1.0 and include a clear comment in any PR so we can refer to the change if asked.
3. **`sponsorship-levels.json`.** Remove it once labels live in the schema, or keep it as a
   generated file for anyone who reads it directly? **SC:** Keep this for now but label it as deprecated; add a future note to decide if we keep this or not.
4. **Dataset registry.** Add `_data/datasets.yml` as the single list of datasets, and do it
   together with the DCAT catalog step? **SC:** Agreed, this is a great simplification of our metadata.
5. **`nonprofitStatus` enum.** Leave it for a separate data cleanup, or start that cleanup
   now? **SC:** Yes, do that as a PR as noted in this plan; this is an important cleanup to do.
6. **Where to start.** Begin with step 1 of the suggested order, or a different one? **SC:** Agreed; begin implementing these PRs.

## Decisions

Shane Curcuru answered every open question on 2026-11-15, in the **SC:** notes above.

1. **New schema keywords.** Use `x-` keywords, and document each schema's keywords in its
   top-level `$comment`. The keyword for fields shown by another include is `x-includes`
   (not `x-display`), naming a file in `_includes/`.
2. **OpenAPI v1.** Generate `openapi/v1/foundation-schema.yaml` from the JSON Schema as
   version 1.1.0, because the changes add fields that earlier users of v1 will want. The
   pull request says clearly what changed, so it can be cited later.
3. **`sponsorship-levels.json`.** Keep it for now, generated from the schema and marked
   deprecated. Whether to keep it at all is a future decision.
4. **Dataset registry.** Add `_data/datasets.yml`, together with the DCAT catalog step of
   the URL standards plan.
5. **`nonprofitStatus` enum.** Clean up the values and add the enum in its own pull
   request, as part of this plan.
6. **Where to start.** Start with step 1 and carry on through the suggested order, one
   pull request per step.

Also decided: leave the `projects-*.csv` files and their pages alone. They were an
experiment.
